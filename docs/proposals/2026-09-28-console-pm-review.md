## 0. 一句话结论

**地基是合格的，产品是缺失的。**

内核、插件扩展点、路径 jail、缓存指纹、错误码信封这些「工程地基」做得相当扎实
（`AC-9` 的指纹机制、`N1` 的响应脱敏、`V6/V7/V8` 的错误映射都是同类项目里少见的严谨）。
但把浏览器打开之后，它不像一件**产品**，而像**把 23 个 CLI 命令搬到网页上，
让用户自己当那台调度机器**。

三个根因（后面所有问题都能归到其中一条）：

| # | 根因 | 表现 |
|---|------|------|
| **R1** | **缺一层「当前公司」的上下文** | 公司是平级页面；图表/报告/迭代三个页面必须由「公司页的链接」带参数进来。用户刷新一下或直接点侧栏，页面就退化成一屏 `BAD_REQUEST`（REQ-009 已登记的 `E2` 就是这个根因的表层） |
| **R2** | **交互抽象停在「命令」层，没有「任务」层** | 白名单命令 + argparse 扫描出来的原始参数直接暴露：`company_dir*`、`output_dir*`、`run_dir*`、`latest`、`force`、`--only-gaps`。用户要自己知道「更新这家公司」= `runs new` + `analysis_status` + 4 步定性管线 + `value_analysis_engine`，还要自己拼路径 |
| **R3** | **没有「状态层」** | 没有首页、没有加载态、没有数据新鲜度、没有执行前预检、没有危险确认、没有失败重试、没有人话空状态。系统当前处于什么状态，只能从降级卡片里反推 |

## 2. 关键改进建议

### 2.1 信息架构：加一层「当前公司」上下文（对应 P-3、P-5、P-6、E2）

你的第 1 点（公司应该是公司功能的上级菜单）我同意**问题**，但建议换一个**解法**：

> **把公司做成「上下文」而不是「父菜单」。**

理由：父菜单是个树，一家公司下面挂「图表/报告/迭代/估值」很顺；但这个项目接下来必然要有
**跨公司**的能力——你已经点名的『一次拉出所有数据』本身就是跨公司的，后面还有选股、组合、多公司对比。
如果公司是父菜单，这些能力只能挂在树外面，用户会问「为什么选股不在公司菜单里」。
上下文选择器（全局）能让「公司级页面」和「全局页面」共存，且**一个 URL 就能表达完整状态**（可分享、可刷新、可前进后退）。

```
┌──────────────────────────────────────────────────────────────────────┐
│  价值分析控制台     [ 公司：600887 伊利股份  ▾ ]  [ 搜索/切换公司 ]   │   ← 全局上下文（可搜索、记住上次）
├───────────────┬──────────────────────────────────────────────────────┤
│ 工作台        │                                                      │
│ 数据          │   页面标题：伊利股份 · 图表                          │
│   ├ 数据获取  │   （面包屑：公司 / 图表）                            │
│   ├ 数据缺口  │                                                      │
│   └ 存储概览  │   [ 数据截至 2026-06-30 · 数据包生成于 09-26 16:41 ] │  ← 新鲜度徽标（对应 P-8）
│ 公司          │                                                      │
│   ├ 概览      │   ┌ chart ────────────┐ ┌ chart ────────────┐       │
│   ├ 图表      │   └───────────────────┘ └───────────────────┘       │
│   ├ 报告      │                                                      │
│   ├ 迭代记录  │                                                      │
│   ├ 估值      │                                                      │
│   └ 买卖计划  │                                                      │
│ 分析（跨公司）│                                                      │
│ 任务          │                                                      │
└───────────────┴──────────────────────────────────────────────────────┘
```

要点：

1. **全局公司选择器**（可搜索、记住上次选择、写进 URL）。选中后所有「公司级页面」自动带上下文，
   不再依赖「从公司页点进来」。
2. **没有选中公司时**：公司级页面显示**正常的空状态**——「先选一家公司，或去看工作台」，而不是
   `BAD_REQUEST` 降级卡。这条同时把 `E2` 关掉。
3. **侧栏分组按「用户要干什么」**，不按「代码在哪一层」：`工作台 / 数据 / 公司 / 分析 / 任务`。
   「按键」这个词消失——动作出现在它所属的对象上（公司页的「更新分析」，数据页的「拉取」）。
4. **公司标识统一**：全站一个显示名（`600887 伊利股份`），目录名 `600887_伊利` 与 `600887.SH`
   只在「技术详情」里出现（对应 P-6）。
5. **工作台做首页**（对应 P-5）：自选股列表 + 每家的状态（数据截止日、上次分析、是否过期、缺什么）+
   「下一步建议」+「一键拉取全部数据」入口。空库时是引导，不是空表。

> 这需要框架支持两件新东西：**导航的父子层级**与**导航项的上下文依赖**。
> 二者都必须走 `REQ-009.3` 的扩展点（`registry.nav(...)` 加 `children` / `requires`），
> **不许改核心**——否则 `AC-9` 的「加功能不改地基」就废了。

### 2.2 交互：从「命令」升到「任务」（对应 P-2、P-4、P-7、P-10、P-12）

这是投入产出比最高的一块。现在的按键页把「项目有 23 个脚本入口」这件事**当成了产品结构**，
但用户心里只有 5~6 件事：

| 用户想干的事 | 现在要做的（界面上） | 应该做的 |
|---|---|---|
| 更新一家公司的分析 | `runs new`(10 参数) → 4 步定性管线(8/4/6/3 参数) → `value_analysis_engine`(3 参数) → `runs finish`(10 参数)，路径与 `run_dir` 全靠手敲 | 一个按钮「更新 600887 的分析」，公司/期次/run 由上下文预填；内部按既有脚本依次编排，每步一个进度条 |
| 拉数据 | `make gui-collect ARGS='--profile frugal --ticker … --period …'`（CLI）+ 一个只读的采集存档页 | 「拉取数据」→ 选范围（这家公司 / 全部自选股）→ 看**预估调用量** → 确认 → 进度 → 结束给缺口摘要 |
| 看这家公司 | 先到公司页，点公司名（才进图表） | 选好公司后直接看概览 |
| 改错了要回退 / 看历史 | `runs · adopt`、`runs · finish`、`history.jsonl` | 时间线上「回看这次」「以这次为基线重跑」 |
| 知道现在缺什么 | 采集存档页 + 自己比对 | 工作台上的「待办」：哪家数据过期、哪个接口无权限 |

具体设计约束（建议写进 AC）：

1. **参数永不手敲**：公司、期次、run 一律来自上下文与下拉；界面上**不允许**出现
   文件系统路径（`output/…`）、内部目录名（`20260926T164155496211Z`）、内部参数名
   （`company_dir` / `output_dir` / `run_dir` / `latest` / `force`）。
2. **执行前预检（pre-flight）**：说清「会发生什么」——联网吗？花配额吗？覆盖还是新增？
   预计多久？前置不满足时按钮**禁用并给出原因**（「先在右上角选一家公司」「没有配置
   TUSHARE_TOKEN」），而不是点下去才报错。
3. **危险动作要确认弹窗**，不是换个按钮文案（对应 P-10）。
4. **任务中心**：队列 / 进行中 / 历史三段；日志**默认折叠**，失败时才自动展开；
   失败给「人话原因 + 下一步」；任务产出**链接到产物**；离开页面任务继续，回来还在（对应 P-12）。
5. **保留可审计性**：真实命令行、退出码、日志一个字都不能少——但要收进「详情」抽屉，
   不是在主界面上当标题（这是现有实现做得好、不要退化的地方）。

### 2.3 视图质量（对应 P-1、P-9、P-8、P-13、P-14）

1. **口径必须先修**（P-1，最紧急）：年度 / 半年 / 单季**不能画在同一根轴上**。
   最小改法：按口径分组——年度一条线（2021…2025），单季/半年另开一组；
   或给一个「口径」切换（年度 / 单季 / 累计），默认年度，并在图上标注「累计 / 单季」。
   这一条与数据层有关：口径应该是**数据自带的结构化信息**，不是靠前端猜列名（见 REQ-011 草案）。
2. **图表按容器宽度 + `devicePixelRatio` 绘制**（P-9），坐标轴标签防重叠（隔项显示还不够，
   要按测量宽度抽稀或旋转），图例换行，y 轴带单位，x 轴带上「累计/单季」标注。
3. **新鲜度徽标**（P-8）：把已经下发的 `panel.meta` 显示出来——「数据包生成于 2026-09-26 16:41 ·
   命中缓存」。并把「刷新视图」（不花钱）和「重新拉取」（花钱）做成两个不同的按钮。
4. **时间线人话化**（P-13）：`2026-09-26 16:41 · 半年报增量更新`；取代关系显示被取代那条的**可读标题**；
   原始 run id 放进详情。
5. **表格加搜索/排序/分页**（P-14）：通用的表格能力，做在渲染器/面板协议层，所有表格受益。
6. **导出**（新增小能力，价值高）：图表存 PNG、表格存 CSV。`canvas.toDataURL()` 就够，
   不需要新依赖——REQ-009 的设计文档本来也把它列为「开放问题」。

### 2.4 文案与一致性（对应 P-7、P-15）

1. **面向用户的错误**：`{发生了什么} + {怎么办}`，错误码折叠进「技术详情」。
   现在是「面板渲染失败：报告阅读 / BAD_REQUEST / 缺少公司目录参数 company」——三行里有两行是给开发者看的。
2. **UI 里禁止出现 CLI 开关**（`--only-gaps` 这类）；按钮旁边应该写「只补缺口」。
3. **术语表**：`采集/存档/批次/缺口` 这些词在界面上要么换成人话（`拉取/已下载的数据/一次拉取/还缺什么`），
   要么在首次出现时给一行解释。
4. **空状态要写人话**：`还没有注册任何页面。` → `这里还没有数据。先去「数据」页拉一次数据，或在工作台导入已有的 output/ 目录。`

### 2.5 为后续迭代预留（你特别提到的「考虑后续功能迭代」）

这些**不要求现在做**，但现在的设计不要把它们堵死：

| 后续能力 | 现在必须预留什么 |
|---|---|
| 一次点击拉全部数据（REQ-011） | 数据页的入口位置、任务中心的编排能力、以及**原始仓的查询接口**——GUI 不应该再解析 Markdown 表格 |
| 多公司对比 / 自选股批量分析 | 「当前公司」是可空的**上下文**（不是单选菜单）；面板协议能接受**一组**标的 |
| 选股 / 组合跨公司视图 | 侧栏要容得下「与公司无关」的页面；公司页不能抢占全局导航 |
| 新图型（K 线、热力图、散点） | `registerPanelKind` 已经是扩展点——保持；但**轴/图例/口径**这些公共能力要抽出来，别让每种图各写一遍 |
| 视图收藏 / 自定义工作台 | 页面描述已经是纯数据（`AC-3.3`）——未来可以存「一份面板配置」，所以**面板描述里不要塞不可序列化的东西** |
| 报告内搜索 / 高亮 / 批注 | 报告目前是服务端渲染的 HTML 片段（`markdown_safe`）——如果要批注，得提前想好锚点策略 |
| 定时提醒（不是定时拉取） | 与 `AC-4.1`「手动触发边界」不冲突，但要提前确认：提醒 ≠ 拉取 |

### 2.6 明确不建议做的

- **不引入前端框架**（React/Vue）与图表库：现在的问题**不是**技术栈问题，改架构换不来 IA。
  零依赖这条底线值得继续保持（CI 与 scope 预算都靠它）。
- **不给「任意命令输入框」**：REQ-009 的 `AC-1.3` 白名单是安全边界，不能为了「灵活」拆掉。
  要灵活就**加按键**（`ENTRIES` 加一行），不是加一个 shell。
- **不为了好看牺牲审计**：真实 argv / 退出码 / 日志是这套工具最值钱的部分。
