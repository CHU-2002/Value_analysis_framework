# REQ-012 控制台 2.0（公司上下文 + 任务式交互 + 视图质量）

## 背景与问题

`REQ-009` 交付的控制台**功能是齐的**（浏览不联网、图表、报告、迭代台账、按键执行、采集存档），
工程质量也扎实（面板级降级、路径 jail、响应脱敏、核心指纹），但产品层缺失，
2026-09-28 的走查结论是**「把 23 个 CLI 命令搬到网页上，让用户自己当调度机器」**。
三个根因（详见走查报告 §0）：

| 根因 | 可复现证据 |
|------|------------|
| **R1 缺「当前公司」上下文** | `公司/图表/报告/迭代记录` 是四个平级 `NavItem`（`plugins/companies.py:328-331`）；冷开 `#report` 或直接点侧栏 → `curl /api/v1/pages/report` 返回 **2 张 `BAD_REQUEST` 降级卡 + 横幅**（`REQ-009` 已登记的 `E2`）；页面上看不到「现在看的是哪家公司」 |
| **R2 交互停在命令层** | 界面顶部回显 `命令行：/Users/…/.venv/bin/python /Users/…/scripts/runs.py resolve …`（`kinds/form.js:92`）；字段是 `company_dir *` / `latest` / `run_id`（由各脚本 argparse 扫描得出）；23 个按键里 **20 个带必填参数**，`runs_new` / `runs_finish` 各 10 个，`下载定期报告 PDF` 12 个。主流程「更新一家公司的分析」需要 6 个按键、路径与 `run_dir` 全靠手敲 |
| **R3 没有状态层** | 没有工作台首页（默认落地页是 `采集存档`，`plugins/collect.py:147` `order=5`）；没有加载态（`app.js` 取完数据才建 DOM）；`panel.meta` 已下发但**没有任何前端渲染器读它**（`grep -rn meta scripts/webui/static/` 只命中 `<meta charset>`），而 `GUI_CONSOLE_OVERVIEW.md` §2.3 承诺过「数据生成时间/缓存徽标」；危险动作没有确认弹窗（只换按钮文案） |

另有两条**正确性/一致性问题**：

- **图表把年报口径与季报口径画在同一根轴上**：`data_pack_market.md` 的列是
  `2026H1, 2026Q1, 2025H1, 2025Q1, 2025, 2024 …`，`plugins/charts.py:61,81` 只做 `reversed()` 就直接画；
  营收曲线出现「115,636 → 32,938 → 61,776」的锯齿。这不是经营波动，是口径混用，
  会让人做出错误判断。修复它需要 `REQ-011` 的结构化口径（见 `REQ-011` 的 `AC-4`）。
- **同一家公司两套名字**：公司页/图表页用目录名 `600887_伊利`，采集存档页用 `600887.SH`。
- 界面文案里出现 CLI 开关（`plugins/collect.py:145`：「补齐请用 `--only-gaps` 收敛目标」）。

## 目标

1. **用户不再需要知道内部结构**：不输入路径、不输入 `run_dir`、不理解 `--flag`；
   面向用户的是「事」，不是「命令」。
2. **「当前公司」是一等上下文**：选一次，全站生效；没选时是正常空状态而不是技术报错。
3. **系统状态可见**：数据截止/生成时间、是否过期、任务进度、失败原因都在界面上；
   「刷新视图（不花钱）」与「重新拉取（花钱）」是两个不同动作。
4. **不牺牲可审计性与可扩展性**：真实命令行/退出码/日志仍然可查；
   新页面/新面板/新图型仍然只加插件不改核心（沿用 `REQ-009.3` 的 `AC-9` 判据）。

## 验收标准

- **AC-1**：**公司是上下文而不是平级页面**——存在一个全局的当前公司选择器（可搜索、可切换、
  记住上次选择），选中后所有「公司级页面」（概览/图表/报告/迭代记录/估值/买卖计划）自动带上下文，
  **不需要经过某个特定页面的链接**；页面标题或面包屑上能看出当前公司；
  当前公司写进 URL，刷新与前进后退后状态一致。
  给定「直接打开 `#report`」与「先选公司再打开 `#report`」两种路径，前者不出现任何 `BAD_REQUEST` 降级卡
  （同时关闭 `REQ-009` 登记的 `E2`）。
- **AC-2**：**工作台首页**——默认落地页是概览而不是某个业务面板，内容至少含：
  当前自选股及其状态（数据截止期次、最近一次分析时间、是否过期/待更新）、待办（缺数据/过期/上次失败）、
  以及直达动作（拉取数据 / 更新分析 / 重建派生数据）。数据为空时给**引导**（下一步该做什么），
  不是空表。给定「全新的空 `output/`」与「已有 12 家公司的 `output/`」两种输入，首页都可用且不报错。
- **AC-3**：**意图化动作，参数不手敲**——用户可见的动作以「做什么」命名（如「更新这家公司的分析」
  「拉取全部数据」「只补缺口」），公司/期次/run 等参数由上下文与下拉预填；
  界面上**不得**要求用户输入文件系统路径、内部目录名或内部参数名
  （`company_dir` / `output_dir` / `run_dir` / `input` / `latest` / `force` 等），
  也不得把 CLI 开关写进面向用户的文案。
  由一条**扫描前端与面板文案**的测试断言：面向用户的字符串里不出现上述参数名/开关/绝对路径。
- **AC-4**：**执行前预检与危险确认**——动作执行前说明将发生什么（是否联网、是否消耗配额、
  覆盖还是新增哪些产物、预计耗时/调用量）；前置不满足时按钮**禁用并给出可读原因**
  （未选公司 / 未配置 token / 上游产物缺失），而不是提交后才报错；
  标记为危险的动作必须经过一次显式确认（弹窗或等价的二次确认控件）才提交。
- **AC-5**：**任务中心**——统一列出队列/进行中/历史任务，含进度、可取消、失败可重试；
  日志默认折叠、失败时自动展开；失败给「发生了什么 + 怎么办」（技术细节可展开）；
  任务产出链接到对应产物；离开页面任务继续运行，回来后仍能看到。
  由测试断言：失败任务的展示里同时含可读原因与可展开的原始日志（两者都不丢）。
- **AC-6**：**数据新鲜度可见**——公司级页面上显示数据来源与生成时间（或「命中缓存」），
  并把「刷新视图」（离线重算，不花钱）与「重新拉取」（联网，花钱）做成两个语义不同的动作；
  两者在界面上可分辨（文案 + 是否需要确认）。
- **AC-7**：**图表口径正确且可读**——趋势图**不得**把年度口径与半年/单季口径画在同一条序列上；
  必须能按口径查看（默认年度），并在图上标明单位与口径（累计/单期）；
  图形按容器宽度与设备像素比绘制（不模糊）、坐标轴标签与图例不被截断/重叠；
  缺失值有可见标注（沿用现有「缺失值断开折线而不是画成 0」的语义）；
  提供导出（图片或数据）。
  给定一份同时含年度与单季期次的数据集，图表输出的序列数 ≥2（年度/单季分组）或带显式口径切换状态（可断言）。
- **AC-8**：**表格可用**——公司列表、产物列表、批次列表、缺口列表支持搜索、排序与分页/限高，
  在 100 行数据下不出现需要肉眼滚动查找的体验；搜索/排序能力做在通用渲染层，不是每个面板各写一遍。
- **AC-9**：**统一公司标识**——同一家公司在全站只有一个显示名（如 `600887 伊利股份`）；
  目录名 `600887_伊利` 与 ticker `600887.SH` 只作为技术标识出现在详情/技术信息里；
  给定同一家公司在公司页、图表页、采集存档页三处出现，显示名一致（可断言）。
- **AC-10**：**面向用户的错误**——所有错误展示含「发生了什么 + 下一步怎么做」，
  技术错误码可展开但不占据主视觉；不得把 `BAD_REQUEST` 之类的错误码作为标题。
  由一条对降级/失败卡片的文案契约测试断言。
- **AC-11**：**扩展性不回退**——新增页面、面板、图型、动作仍然只新增插件文件、不改核心；
  新增的导航层级与「上下文依赖」必须通过注册表扩展点实现（`REQ-009.3` 的 `AC-9` 指纹判据继续成立）。
- **AC-12**（实跑）：用**真实浏览器**走查「新用户第一次打开 → 选公司 → 看图表/报告/迭代 →
  执行一个动作 → 观察失败与重试 → 切换公司」全路径，逐屏截图留证，
  并断言全程**没有任何技术化错误页**（除人为构造的失败场景外，零 `BAD_REQUEST` 类卡片）。

## 范围

**包含**

- 全局公司上下文与信息架构重排（含工作台首页）。
- 任务式动作层（意图化动作、预检、确认、任务中心、多步编排）。
- 视图质量：图表口径修正与绘制质量、数据新鲜度显示、通用表格能力、错误/降级文案。
- 统一公司标识。
- 数据页（在 `REQ-011` 之上接线）。
- 为以上能力所需的**框架扩展点**（导航层级、上下文声明、通用表格/轴能力），按 `REQ-009.3` 的方式演进。

**不包含**

- 数据获取与存储本身（属 `REQ-011`；本需求只消费它的仓与动作）。
- 引入前端框架或第三方图表库；前端构建链（Node/npm）仍然不引入。
- 远程访问、多人使用、鉴权与用户体系（沿用 `REQ-009` 的安全边界，将来另开 REQ）。
- 在面板里编辑产物或报告（本期仍只读优先；写操作走既有脚本/动作）。
- 定时/自动拉取或自动分析（`REQ-009.4` 的 `AC-4.1` 手动边界不变）。
- 移动端适配与主题定制。
- K 线缩放、专业图表皮肤等「图表花活」（新增图型可以，但属后续切片的自由裁量，不在本期承诺）。

## 约束与依赖

- **零新增依赖**：手写前端 + Python 标准库这条底线不变（CI 只装 `requirements-test.txt`）。
- **不改核心的原则不变**：新能力通过注册表扩展点落地；确实必须动 `core/*` 或 `static/app.js` 时，
  按 `REQ-009` 的先例留痕（核心指纹同步 + 在需求里说明动的是「扩展面」还是「缺陷」），
  并由独立评审者确认是否影响 `REQ-009.3` 的既有结论。
- **安全边界不变**：只监听 `127.0.0.1`；路径 jail 覆盖新增的数据根（`REQ-011` 的仓若在 `output/` 之外，
  必须显式新增允许根，不是放宽 jail）；token 不出现在界面与日志。
- **可审计性不变**：真实 argv、退出码、日志必须仍然可见（收进详情，不是删除）。
- **依赖**：`REQ-009`（框架与既有视图）、`REQ-011`（数据层，`REQ-012.4` 的前置）、
  `REQ-010`（最新价值报告指针——工作台与估值页要显示 `stale`/`unavailable` 状态）。
- **测试预算**：`REQ-009` 的 4 个 webui 测试文件已 **64/64 零余量**（`AC-7` 是 `REQ-009` 自己的上限，
  不得为了让新测试挤进去而放宽）。本需求必须新开测试文件；仓库总预算当前
  **38/48 文件、1653/1800 用例（92%）**，登记前应先给出本需求的用例预算，
  并按「先清理再谈上调」的纪律处理。

## 备注

- **与 `REQ-009` 的关系**：`REQ-009` 已 `verified`，本需求**不修改**它的任何 `AC`，
  也不回退它的安全边界与手动触发边界；它登记过的残留项里，`E2`（空选择冷启动降级）
  由 `REQ-012.1` 的 `AC-1.1` 关掉。其余残留（`V2` 路由先匹配后解码、`V3`/`V9` 坏子条目连坐与根目录语义、
  `V4` 非 tty 缓冲）与本需求无直接关系，仍留在 `REQ-009.3` 的下一次框架演进里。
- **先修 P-1 的建议**：走查报告里的 `P-1`（图表混口径）是**正确性问题**，会误导投资判断。
  它既可以作为 `REQ-012.3` 的第一件事，也可以先按 `docs/requirements/README.md` §6
  走 `REQ-009` 的「维护记录」做**最小修复**（年度/单季分组或加口径切换），不必等 IA 大改。
  若走最小修复，`REQ-012.3` 只需承接「更好的口径交互」而不是「改正错误」。
- **风险：IA 大改会动到已经验收过的扩展面**。`static/app.js` 在核心指纹清单里，
  导航层级/上下文选择器很可能需要改它。缓解：把扩展点增量做成**框架切片**（类似 `REQ-009.3` 的地位），
  先交付扩展点 + 演示插件 + 指纹更新，再由业务切片消费；每个切片收口前先跑走查
  （`REQ-009` 的 `E1` 教训：面板级 AC 全绿 ≠ 页面可用）。
- **开放问题 1**：公司上下文是「单选」还是「可按标签筛选的一组」（影响将来多公司对比与批量分析）？
  建议先按可空单上下文落地，但**数据模型上不要假设只有一个**。
- **开放问题 2**：工作台上的「待办」判定规则（数据过期 / 下游 stale / 上次失败）是否需要独立需求？
  建议先作为 `REQ-012.1` 的一部分实现，规则写进设计文档。
- **开放问题 3**：`REQ-010` 的价值报告 `stale`/`unavailable` 状态要不要在公司概览页显眼提示？
  建议要，且纳入 `REQ-012.1` 的公司概览（不影响 `REQ-010` 自身验收）。
