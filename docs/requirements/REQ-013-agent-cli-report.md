# REQ-013 一键生成分析报告（程序化调用 agent CLI）

## 背景与问题

这个项目的「分析」由两段拼成，中间隔着一次 **LLM 调用**（`ARCHITECTURE.md` §2）：

```
确定性前段（Python）                     人/agent 段                              确定性后段（Python）
取数 → 下载 PDF → 解析章节 → prepare  →  模块 Agent D1~D7 + Final Synthesis  →  reconcile → synthesis → resolve
```

- **LLM 那一段今天只能在 Claude Code / OpenCode 里人工跑**：`.claude/commands/*.md` 与
  `.opencode/commands/*.md` 是给 agent CLI 读的提示词文件（`/business-analysis` /
  `/update-analysis` / `/value-analysis` 等 7 个）。
- 仓库里**没有任何程序化 LLM 入口**：无 SDK、无 API key、无 HTTP 调模型的代码（已核实）。
- `REQ-009` 交付的控制台因此只能跑两端的确定性步骤；用户在界面上点完 `prepare` 之后，
  必须**自己切到终端**、自己想起该跑哪个 slash 命令、跑完再切回来点后面几步
  （`REQ-012` 的 `AC-2.4` 只要求界面**交接**这件事，不要求自动化）。
- 而 agent CLI 本身**支持非交互调用**（已核实：`claude` 在 `PATH` 上，`claude --help` 明确写着
  「use -p/--print for non-interactive output」；`opencode` 也在 `PATH` 上）。
  这意味着「一键出报告」在技术上是可达的——缺的是把它做成一个**有边界、可审计、有确认**的能力。

## 目标

1. **一键**：在控制台选一个动作 + 一家公司，点一次就能跑完「agent 段」并把结果落到既有产物位置。
2. **有边界**：只有**枚举的动作**，没有自由文本 prompt；标的必须能校验；不用 shell；GUI 不碰任何凭据。
3. **可审计**：每次执行是一个任务，能看到完整命令行、状态、退出码、日志尾部与产出文件。
4. **不越界**：仍然只能由人点触发（没有定时器、没有自动重跑），并且执行前明确告知「这会消耗模型额度」。

## 验收标准

- **AC-1**：**动作白名单**——可触发的 agent 动作是**枚举**的（首版：`update-analysis` 更新分析报告、
  `business-analysis` 首次全量分析、`value-analysis` 价值分析报告），每个动作对应**一条固定的**
  固定指令模板，由所选 CLI 适配（动作语义为 `/<action> <ticker>`）；界面与接口都**不接受自由文本**进入命令。
  给定一个不在枚举里的动作名，接口返回 4xx 且**不启动任何外部进程**（可断言）。
- **AC-2**：**标的白名单校验**——`ticker` 必须先通过校验才允许执行：形如 `600887.SH` / `00700.HK` /
  `AAPL`（沿用 `scripts/config.py::validate_stock_code` 的规范化），且在本机公司目录里能找到对应标的
  （`output/<code>_*/`）。校验失败时返回 4xx、给出人话原因、**零外部进程**（可断言）。
- **AC-3**：**无凭据通路**——GUI 不接收、不存储、不回显任何 agent/模型凭据；认证完全由 agent CLI
  自身的登录态与环境决定；任务记录与日志里的凭据按既有 `core/security.py::redact` 规则脱敏。
  由一条断言（响应与日志里不出现环境变量中的凭据值）。
- **AC-4**：**执行前告知与确认**——启动前能看到**将执行的完整命令行**（动作 + 标的 + 解析出的 CLI 路径），
  并明确提示「会消耗模型额度 / 可能需要较长时间」；需要一次显式确认（复用既有 `danger` 语义）才提交。
- **AC-5**：**任务化与审计**——每次执行是一个任务（复用既有任务运行器）：有状态、退出码、可取消、
  日志尾部；任务记录保存动作 id、规范化后的标的、完整命令行（脱敏后）、开始与结束时间；
  任务完成后给出**产出文件**的链接（报告/变化报告/run 目录）。
- **AC-6**：**失败可读且零副作用**——agent CLI 不存在或不可执行时，返回明确提示（含安装/登录指引）
  且**不留下任何半成品**；退出码非 0 时给「发生了什么 + 怎么办」的人话摘要，原始日志可展开；
  **不自动重试**。
- **AC-7**：**手动边界不变**——只能由显式点击 / CLI 子命令触发；不引入定时器或调度器
  （沿用 `REQ-009.4` 的 `AC-4.1`）；同一（动作, 标的）不允许并发跑两个，第二次返回明确错误码。
- **AC-8**（实跑）：由 owner 或常设授权的 agent 用**真实的 Codex/dsh 登录态**跑一次「更新 600887 的分析」，
  记录：可复制命令、耗时、模型消耗量级、产出文件（报告 / 变化报告 / run 目录）与本次发现的问题去处。
  报告里**不写**任何凭据。

## 子需求

### REQ-013.1 包装脚本与动作白名单

- 状态：`verified`
- 目标：把「动作 + 标的」翻译成一次 agent CLI 的非交互调用，并在脚本层做全部参数校验。
- 验收标准：
  - **AC-1.1**：一个仓库内脚本接受 `--action`（枚举）与 `--ticker`（校验），映射成固定的 agent 命令模板；
    未知动作 / 非法标的一律非 0 退出且不启动外部进程（对应 `AC-1`/`AC-2`）。
  - **AC-1.2**：调用 agent CLI **不经过 shell**（`shell=False`，参数是列表），CLI 可执行文件可配置
    （`--cli` / 环境变量），找不到时给出安装/登录指引并退出（对应 `AC-6`）。
  - **AC-1.3**：脚本支持 `--dry-run`：只打印将执行的命令行与解析出的路径，不启动任何进程。
  - **AC-1.4**：退出码与 agent CLI 的退出码一致地透传（非 0 即失败），并支持 `--timeout`。
- 追溯：`tests/test_agent_action.py`；PR #114, #115

### REQ-013.3 提交前预检、完整命令行与产出链接

- 状态：`verified`
- 目标：把「点了才知道」变成「点之前就知道」——把 `REQ-013.2` 交付时超出本片能力的三件事补齐

- 验收标准：
  - **AC-3.1**：**提交前**（不产生任务）就能看到将执行的**完整命令行**（含标的）与

  - **AC-3.2**：**预检**——agent CLI 不可用、或标的与公司目录不匹配时，页面上的按钮

- 追溯：`tests/test_agent_action.py`；PR #114, #115

## 范围

**包含**

- 白名单 agent 动作（首版 3 个）与它们到 agent CLI 非交互调用的映射。
- 一个仓库内的包装脚本（参数校验、命令行拼装、退出码透传、`--dry-run`、`--timeout`）。
- 控制台的一个最小页面（选动作 + 标的 + 确认 + 任务日志 + 产出链接），复用既有注册点与渲染器。
- 用**假 CLI**（`tmp_path` 里的小脚本）做的自动化测试。

**不包含**

- **自由文本 prompt 输入**（这会同时带来注入与不可审计两个问题）——要什么动作就**加一个枚举值**。
- GUI 里的凭据输入、模型选择、温度之类的推理参数（认证与模型由 agent CLI 自己的配置决定）。
- 多步确定性链的编排、预检/交接协议（属 `REQ-012.2`；本需求不依赖它，也不替代它）。
- 定时 / 后台 / 自动重跑；并行批量多标的（后续演进，需另立判据）。
- 把 agent 的输出**再加工**成报告（那是 agent 段自己的职责；本需求只负责触发与收口）。

## 约束与依赖

- **零新增依赖**：只用 Python 标准库与仓库既有依赖。
- **不用 shell**：参数以列表传递，`shell=False`；动作与模板是常量，标的是校验过的值——
  这三条合起来保证「用户输入永远不进入命令字符串的语法位置」。
- **不改核心**：本需求的最小实现只新增一个脚本与一个插件；`core/*` 与 `static/app.js` 不动，
  `REQ-009.3` 的 `AC-9` 核心指纹**不应变化**（若确实需要动，按 `REQ-009` 的先例留痕并由独立评审者确认）。
- **与 `REQ-012` 的关系**：`REQ-012.2` 的 `HumanStep`（交接）是**手动**形态；本需求是**自动**形态。
  两者并存：同一条链既可以选择「我来跑」也可以选择「让它跑」。本需求**不要求** `REQ-012.2` 先交付。
- **依赖**：`REQ-009.1`（任务运行器：白名单、异步、取消、日志、历史）与 `REQ-009`（面板/路由注册点）。
- **测试预算**：仓库预算 2026-09-28 上调为 **52 文件 / 2000 用例**（`REQ-006` 的 `AC-7` 与任务 T9）；
  本需求规划 **1 个测试文件**、合计 ≤ 25 条用例，全部用假 CLI，**不调用任何真实模型**。

## 备注

- **受理记录**：2026-09-28 由使用者（CHU-2002）受理。原话：「我们后面再开 req 实现一键出报告，
  你可以给这个 req 建个最简单的界面，提交到远程」；同时明确 `REQ-012` 内先按「人机交接」形态
  （`AC-2.4` 修订）落地，本需求随后做自动化。
- **切片决策（2026-09-28）**：本需求实际分三步走——`.1`（包装脚本 + 白名单，已完成）、
  `.2`（最小界面，已完成，证明了「不改 core/static 也能做出可用界面」）、
  `.3`（提交前预检 / 完整命令行 / 产出链接，会动 `static/kinds/form.js` 这个扩展面）。
  使用者选择把 `.3` 单独立片，而不是把 `REQ-013` 的收口挂到 `REQ-012.2` 上。
- **为什么不做自由文本 prompt**：`REQ-009.1` 的 `AC-1.3` 把「不经过 shell / 参数白名单」立成安全边界；
  一个自由文本输入框等于把「agent 会执行什么」重新交回给用户随手输入，且日志里无法审计
  （同一动作的两次执行不可比）。要新能力就加枚举值 + 一条命令模板。
- **凭据与付费（开放问题 1）**：本需求用 agent CLI 自身的登录态，因此「谁付钱」由使用者的
  Claude 订阅 / API key 决定，GUI 不参与。若将来要支持多档模型或团队共享凭据，**另开 REQ**。
- **被 agent 改动的工作区（开放问题 2）**：agent 段会读写 `output/<公司>/`。本需求不引入沙箱，
  依赖既有约定（只动该公司的产物目录）。若将来要限制，需要一个新的「工作目录白名单」能力。
- **与「手动边界」的关系（开放问题 3）**：`REQ-009.4` 的 `AC-4.1` 管的是**远程数据采集**（花钱买数据），
  本需求是**本机模型调用**（花额度）。两者都保持「只能由人显式触发」，但错误码与提示文案要各自清楚。
- **开放问题 4**：首版只支持 `claude`（`-p` 非交互）与 `opencode`（若其非交互入口确认后）？
  还是抽象成「任何符合 `AGENT_CLI` 约定的可执行文件」？沿用后者的接口形状、只实现前者，
  由 `--cli` 覆盖（避免为第二个 CLI 写第二套分支）。
