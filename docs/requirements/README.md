# 需求管理

本目录是项目的**需求唯一权威来源（single source of truth）**。任何「要做什么、做到什么程度、算不算做完」的问题，都以这里的条目为准；设计文档、Issue、PR 都是需求的**下游**。

配套文档：

- 测试策略与追溯规则：[`docs/TESTING.md`](../TESTING.md)
- 开发流程与就绪/完成定义：[`docs/DEVELOPMENT.md`](../DEVELOPMENT.md)
- 分支、提交、CI、评审约定：[`CONTRIBUTING.md`](../../CONTRIBUTING.md)

## 1. 三层结构

```
需求 (本目录)          设计 (docs/*.md)              任务 (GitHub Issue / PR)
要做什么、验收标准  →   怎么实现、取舍、接口      →   一次可评审的改动
REQ-NNN                 ARCHITECTURE / *_PLAN          issue → feat/* → PR
```

规矩只有一条：**需求写「要什么」，设计写「怎么做」，两者不互相复制。**
需求条目可以短，但验收标准必须可判定；设计可以长，但不改验收标准。

## 2. 目录内容

| 文件 | 作用 |
|------|------|
| `README.md` | 本文件：编号规则、状态机、优先级、操作步骤 |
| `TEMPLATE.md` | 需求条目模板，新建需求时复制 |
| `ledger.md` | **需求台账**：全部需求的单一索引与状态总览（含「子需求台账」表） |
| `REQ-NNN-*.md` | 单条**大特性**：背景、验收标准、范围、追溯；它拆出的子需求写在同一文件的「## 子需求」小节里（§6.1） |

`ledger.md` 与 `REQ-*.md` 的一致性由 [`tests/test_requirement_traceability.py`](../../tests/test_requirement_traceability.py) 强制校验，**台账漏登记或编号对不上会让 CI 失败**。

## 3. 编号规则

- 需求编号：`REQ-NNN`，三位十进制、单调递增、**永不复用**。删除的需求保留编号并置为 `rejected` / `superseded`。
  一条 `REQ-NNN` 就是**一个大特性**（一整块用户可见的能力）。
- 子需求编号：`REQ-NNN.S`，`S` 在父需求内从 1 单调递增、**永不复用**；写法、状态与验收见 §6.1。
  子需求不单独成文件，也**不能脱离父需求存在**。
- 验收标准编号：父需求条目内 `AC-1`、`AC-2`……；子需求写作 `AC-S.n`（如 `REQ-006.2` → `AC-2.1`）。
  序号在本条（子）需求内唯一。
- 分支与提交沿用 [Conventional Commits](../../CONTRIBUTING.md#提交规范)；PR 描述写 `REQ-NNN`，
  子需求写完整编号 `REQ-NNN.S`，使 GitHub 能反查。

## 4. 状态机

| 状态 | 含义 | 允许的下一步 |
|------|------|--------------|
| `proposed` | 已登记，尚未确认要做 | `accepted` / `rejected` / `deferred` |
| `accepted` | 已确认要做，验收标准已定稿 | `in-progress` / `deferred` / `superseded` |
| `in-progress` | 有分支/PR 正在实现 | `implemented` / `deferred` / `superseded` |
| `implemented` | 代码已合入 `main`，**尚未**逐条验收 | `verified` / `in-progress`（验收不通过时回退） |
| `verified` | 逐条验收标准已核对通过，测试可追溯 | 终态（除非 `superseded`） |
| `deferred` | 本期不做，保留编号 | `accepted` |
| `rejected` | 决定不做 | 终态 |
| `superseded` | 被新需求取代，须写明 `supersedes` | 终态 |

硬性约束：

- `implemented` 与 `verified` 的需求**必须**在测试里有 `REQ-NNN` 引用，否则追溯测试失败。
  （子需求同理：`implemented` / `verified` 的子需求必须在测试里有 `REQ-NNN.S` 引用。）
- 状态只能「逐级前进」；要回退必须同时在条目里记一句原因。
- **父需求的状态不得比它最慢的子需求更靠前**：只要还有一个子需求停在 `in-progress`，
  父需求就不能是 `implemented` / `verified`（旁路终态 `deferred` / `rejected` / `superseded` 不参与比较）。
  这条把「拆子需求」和「偷偷少验收」区分开，由 `tests/test_requirement_traceability.py` 强制。
- **状态与台账必须同一次改动内同步**，禁止只在代码里改而忘了台账。

## 5. 优先级

| 级别 | 判据 |
|------|------|
| `P0` | 阻断主流程 / 数据正确性问题 / 安全问题，需立即处理 |
| `P1` | 当前迭代目标，或已交付能力的必要补全 |
| `P2` | 有价值的改进，可排期 |
| `P3` | 想法与探索，不承诺时间 |

## 6. 粒度：一条需求 = 一个大特性

需求单要能回答「**这个功能做完了没有**」，所以编号是稀缺资源，不能见事就开：

- **新编号只给新能力**。参照现有的：REQ-003/004/005 是「定期报告增量更新」这一个能力的
  三个阶段；REQ-006 是「需求-测试-开发流程」。反面例子：「给某脚本加个参数」「修一下某条
  门禁的判定」都不该各占一个编号。
- **对已交付能力的零散修正**（缺陷修复、门禁细化、文案纠正、小的性能改动）写进该需求的
  「## 维护记录」小节，**不新开编号**。它们仍走同样的 PR 与门禁，只是不再有独立的需求
  生命周期，避免需求单被碎成一地。
- 判断标准很简单：

  | 情形 | 归属 |
  |------|------|
  | 引入用户可见的新能力、新数据流或新命令 | **新需求** |
  | 大特性内部能单独交付、单独验收的切片 | 该需求的**子需求** `REQ-NNN.S`（§6.1） |
  | 只是让某个既有行为变得正确、或把既有能力补完 | 既有需求的**维护记录** |
  | 已交付需求里**没做完**的验收标准 | 该需求状态回退 `in-progress`，不开新需求 |

- 一条需求内部的阶段可以分批交付（用 `depends-on` 与 `pr` 记录），不要为每一批开新号。
- **常设需求**：某些领域是持续维护的（如「工程化开发流程」），做法是**一条需求 + 一张任务清单**：
  需求本身保留该领域的能力判据（AC），具体工作包写成任务（带状态与证据），不各占一个编号。
  参见 [`REQ-006`](REQ-006-requirement-test-dev-flow.md) 的「## 任务清单」。
  （反面教材：2026-09-20 我先后为这块开了 REQ-007、REQ-008、REQ-006.1，被使用者纠正后
  全部并入 REQ-006 的任务，编号置 `superseded`。）

### 6.1 大特性怎么拆：子需求（`REQ-NNN.S`）

大特性内部可以拆，但只有下面三种东西，别再造第四种：

| 层级 | 编号 | 判据 | 能不能独立验收 |
|------|------|------|----------------|
| **需求**（大特性） | `REQ-NNN`，一个文件 | 一整块用户可见的能力，能对外讲清「做完之后能做什么」 | 能：整体判据 `AC-n` |
| **子需求** | `REQ-NNN.S`，父文件里的 `### ` 小节 | 大特性里能**单独交付、单独验收**的切片 | 能：自己的 `AC-S.n` |
| **任务** | `T1`、`T2`…（常设需求的「## 任务清单」） | 不新增用户可见能力的工程性工作：流程维护、门禁加固、文档校正 | 不能：只要证据链接 |

判断顺序只有一个问题：**它能不能被独立验收？** 能 → 子需求；不能但它对用户可见 → 它就是大特性本身，
不该再拆；都不能 → 任务。

写法（不单独成文件，写在父需求文件的「## 子需求」小节里；模板见 [`TEMPLATE.md`](TEMPLATE.md)）：

```markdown
### REQ-NNN.2 摘要缓存

- 状态：`in-progress`
- 目标：重复分析不再重算摘要。
- 验收标准：
  - **AC-2.1**：同一输入连续两次分析，第二次不再调用摘要模型。
  - **AC-2.2**：输入 sha256 变化后缓存失效并重算。
- 追溯：`tests/test_summary_cache.py`；PR #TBD
```

硬性约定（标注了〔CI 强制〕的由门禁把关，其余是写作约定，评审者看）：

1. **编号**：`S` 在父需求内递增、永不复用；子需求不另立文件，也不能脱离父需求存在。
   小节必须写在父需求文件的「## 子需求」小节里、编号不得重复。〔CI 强制〕
2. **AC 编号**：子需求写 `AC-S.n`（`REQ-NNN.2` → `AC-2.1`），父需求自己的判据仍是 `AC-n`。
   两套编号互不顶替：子需求的 `AC-1.1` **不能**当作父需求 `AC-1` 已验收的证据。
   与之配套的一条更关键：**把某条需求（父或子）的状态推到 `verified` 的那个 PR，
   必须把该编号写进「## 需求编号」批次**——否则「只申报一个更窄的子需求编号」就能让父需求的
   `AC-n` 永远不必被核对。〔CI 强制，`scripts/acceptance_gate.py`〕
3. **状态**：子需求有自己的状态（同一套状态机），且父需求不得比它最慢的子需求更靠前（§4）。〔CI 强制〕
4. **台账**：`ledger.md` 的「子需求台账」表逐行登记，与文件里的小节严格一致（不重不漏、状态一致）。〔CI 强制〕
5. **验收按子需求收口，不按 PR**：独立验收只在某个编号推进到 `verified` 时做**一次**——
   那个 PR 在「## 需求编号」里署名该编号，报告就按 `### REQ-NNN.S`（或 `### REQ-NNN`）分节
   逐条打勾；没有状态推进的 PR 一律不看报告。〔CI 强制〕
6. **测试归属**：注释写完整编号 `# 覆盖需求：REQ-NNN.S`。〔CI 强制〕
7. **回归计数**：批量全量回归的计数看的是 `main` 上的特性合入提交（`feat(...)` 或 merge 提交），
   与编号粒度无关——拆子需求既不额外增加一次计数，也不减少；阈值仍是 3。〔写作约定〕
8. **不该拆的情况**：拆出来的切片如果只能和兄弟一起验收、或写不出自己的可判定 AC，
   它是任务而不是子需求。**把一条需求碎成八个编号**正是这套机制要避免的失败模式
   （2026-09-20 的教训见本节开头）。〔写作约定〕

已登记的 `REQ-001`…`REQ-006` **不回填重构**：为形式重排已验证的需求收益为零、风险不小；
新的大特性从登记时就用这个结构。

## 7. 新增一条需求

0. 先按 §6 判断粒度：如果它只是对已交付能力的零散修正，写进那条需求的「维护记录」即可，不要新开编号。
1. **先开 Issue**（`功能请求` 模板），在 Issue 里把背景和期望写清楚，拿到初步共识。
2. `cp docs/requirements/TEMPLATE.md docs/requirements/REQ-NNN-<slug>.md`，填 front matter 与验收标准。
   - 写不出**可判定**的验收标准，说明需求还没想清楚，停在 `proposed`。
3. 在 `ledger.md` 的「需求台账」表加一行，状态填 `proposed`。
4. 只做这一步也可以单独提 PR（`docs(req): register REQ-NNN`），让需求先被评审再写代码。
5. 需求被受理后 → `accepted`，并在 GitHub 建里程碑；开始编码 → `in-progress`。

### 7.1 实跑发现的问题怎么落地

CI 是**全 mock** 的（不联网、不需要 token），它是快而稳的回归网，但测不到三类问题：
**外部数据源的真实行为**（协议、限流、403）、**运行环境的约束**（只读 HOME、权限）、
**真实载荷的规模**（上下文预算装不装得下）。这三类只有**实跑**才能发现。

规则：

- 涉及上述三类的能力，验收标准里必须有一条写「**实跑**」的判据（命令 + 环境 + 预期观察）；
  这类编号收口时，`scripts/acceptance_gate.py` 会强制报告里带「## 实跑记录」小节（含可复制的命令），
  只有 mock 测试的报告会被拒。
- **实跑发现的每个问题当次登记**：能独立验收的写成子需求（`REQ-NNN.S`），
  纯工程性的写成常设需求的任务；并在需求的「## 实跑记录」里留下环境与命令。
- **不允许「只用运行时补丁绕过」**：临时补丁（monkeypatch、改环境变量、手工改文件）可以救急，
  但必须当次登记为待修项——补丁本身就是修复对象（参见 [`REQ-006.1`](REQ-006-requirement-test-dev-flow.md)
  的背景表：一次实跑暴露 6 个问题，全部只靠补丁绕过）。
- 实跑不需要在 CI 里跑：CI 只守住「mock 下的回归」，真实运行由收口时的实跑记录负责。

## 8. 变更与废弃

- **修改验收标准**：属于需求变更，必须在条目内新增 `AC-n` 或显式标注被替换的旧条款，并同步更新关联测试。
  不允许偷偷改小标准让测试通过。若修改**收窄**了判据（例如原条款按字面不可满足），
  条目内必须留下变更记录：原条款原文、变更原因、新条款、批准人（需求 owner），
  并告知独立评审者复核——静默收窄视为违规。
- **范围扩大**：新开一条 `REQ-NNN`，用 `depends-on` 关联，不要把两条需求揉进一条；
  若扩大的部分只是**同一大特性内的一个切片**，登记为该需求的子需求（§6.1），不新开父编号。
- **放弃**：状态置 `superseded` 并填写 `supersedes` / `superseded-by`，或 `rejected` 并写明理由。

## 9. 与 GitHub 的映射

| 本目录 | GitHub |
|--------|--------|
| 需求 `REQ-NNN` | 一个 Issue，标题前缀 `[REQ-NNN]`，标签 `type:requirement` |
| 优先级 `P0`–`P3` | 标签 `priority:P0` … `priority:P3` |
| 领域 | 标签 `area:data` / `area:report` / `area:pdf` / `area:results` / `area:value` / `area:portfolio` / `area:screener` / `area:tooling` |
| 一次交付 | PR，标题 `feat(scope): ...`，正文写 `REQ-NNN`；合并后回填台账 `pr` 字段 |
| 一个阶段 | Milestone，与 `ledger.md` 的「里程碑」小节一一对应 |

GitHub 是**协作视图**，不是权威来源：Issue 可以先于需求存在，但代码合入前需求必须已登记。
Issue 在**验收通过后**才关闭（`verified`），不在 PR 合并时自动关闭——否则等于跳过验收。

## 10. 与测试、开发的接口

| 接口 | 约定 | 校验方式 |
|------|------|----------|
| 需求 → 测试 | 测试文件用注释 `# 覆盖需求：REQ-NNN`（子需求写 `REQ-NNN.S`）声明归属；关键条款在注释里写 `AC-n` / `AC-S.n` | `tests/test_requirement_traceability.py` |
| 需求 → 开发 | 分支名 `feat/<slug>`，PR 正文的「## 需求编号」小节必须真的填（正文提及不算；子需求写完整编号 `REQ-NNN.S`） | PR 模板 + `scripts/pr_body_guard.py` |
| 需求 → 验收 | 只有把编号推进到 `verified` 的**收口**才要独立验收报告（一个子需求/大特性一次）；该编号必须写进「## 需求编号」批次署名，报告逐条核对它自己的 `AC-n` / `AC-S.n` | `scripts/acceptance_gate.py` |
| 开发 → 需求 | 合并后把状态推到 `implemented`；逐条验收后推到 `verified` 并关闭 Issue | 台账 review |
