## 未通过 / 存疑项

1. **【需 owner 明确接受，非阻断】去掉 Python 3.10 的 CI 腿 = 减少验证广度，不是「更严」。**
   `README.md:4`（badge `Python 3.10+`）、`README.md:31`、`CONTRIBUTING.md:27` 都声称支持 3.10，
   而现在每个 PR 只验 3.12。它**没有改变任何判定**（覆盖率、测试、门禁口径都没动），也没有让任何原本失败的
   PR 变绿，故不构成 AC-7 的「放宽判定」；但它是 T5 里唯一一条方向为「更省」而非「更准/更严」的改动。
   实现者自己在 PR 正文里也承认「3.10 那条腿跑在并行 job 里，其实不拖慢总时长，去掉是为了减 compute 与 job 数」。
   我的判断：**可以接受，但要显式留痕**（`REQ-006` T5 行与「T5 交付内容」已写，建议再在条目里标一句
   「3.10 支持改为手动核验」），并且如果要保持「声称支持就自动核验」，更合适的做法是给全量测试加回一个
   **只跑测试的 3.10 矩阵腿**（成本远小于旧的双份 job，因为只有 1 个 job 做矩阵，其余门禁不必重复），
   而不是完全移除。是否值得由 owner 决定。
2. **【非阻断，观察】同 job 串行导致「早期门禁失败 → 后面的门禁不跑」。** 这是「便宜的先跑」的直接副作用：
   本 PR 的真实 run 就因验收步骤失败而**跳过了批量回归与全量测试**。它不放宽合并条件
   （`ci-success` 仍要求整个 job 成功），但意味着一次 run 未必能同时暴露多处问题，且失败的 PR 不会跑到全量测试。
   若希望「即便门禁失败也拿到测试结果」，可给全量测试步骤加 `if: always()`（代价是失败 PR 也耗满测试时间），
   或保持现状换取快速反馈。两种都可接受，建议在 `docs/TESTING.md` 的「CI 的形态」里点明这条取舍。
3. **【非阻断，文档小瑕疵】旧的 job 名仍出现在个别文档里。** `docs/DEVELOPMENT.md:159` 的「出处」列写
