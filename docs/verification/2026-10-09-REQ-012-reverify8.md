### P1 等待点到底等到了什么（当前代码，无任何注入）

```
submit 返回后（内存里还在跑） : 文件存在、1569 字节、可解析 status=running
内存看到 finished 的那一刻    : 文件存在、1569 字节、可解析 status=running   ← 最后一次写还没落地
「只看存在」等待点返回        : 0.000s，文件仍是 1569 字节 status=running    ← 它根本不是等待点
「等终态」等待点返回          : 0.389~0.427s，文件 1999 字节 status=finished
```

⇒ 第八轮那条证伪**成立且仍然成立**：「文件存在」不是等待点（文件在 `submit()` 阶段就已落盘）。
**但这批把产品侧改成了原子写之后，「等待点无效」不再等于「丢数据」**——见 P2 的第 1 行。

### P2 我的 2×2 前后对照（慢盘 0.4s，每格跑 3 次）

| 写入侧 | 等待点 | 重启后读回的 count | 重启后该任务 status | 等待点耗时 | 复刻用例的两条断言 |
|--------|--------|--------------------|---------------------|------------|--------------------|
| **当前（原子写）** | 旧（只看存在） | **1 / 1 / 1** | `failed`（`已中断`） | 0.000s | `count>=1` ✅ / `status==finished` ❌ |
| **当前（原子写）** | 新（等终态） | **1 / 1 / 1** | `finished` | 0.389 / 0.409 / 0.411s | ✅ / ✅ |
| 非原子（父提交写法） | 旧（只看存在） | **0 / 0 / 0** | —（根本没读回来） | 0.000s（读到 **0 字节**） | `assert 0 >= 1` ❌ |
| 非原子（父提交写法） | 新（等终态） | **1 / 1 / 1** | `finished` | 0.398 / 0.405 / 0.413s | ✅ / ✅ |

读法（这是本轮 F1 的核心判断）：

- **原子写把「丢历史」这个后果堵死了**：即使等待点还是那个无效的 `exists`，重启后**照样读回 1 条**
  （因为文件任何时刻都是「完整的一份」，最坏是内容旧一点 → 被 `_load_history` 标成「已中断」）。
  非原子写那一行才是第八轮复现的 `assert 0 >= 1`。
- **等待点的修改解决的是另一半**：没有它，重启时可能读到 `status=running` 的旧内容，
  于是 `reloaded["status"] == FINISHED` 判红（第 1 行最后一列）。两条改动**各修一半，合起来才闭环**。
