## 阻断项 / 非阻断项

### 阻断项

**B1（阻断，高）离线重建静默删行：同一期次多行的数据集只剩 1 行**

- 现象：`datalayer.access.DataAccess._replay` 在**只有一条记录时也**执行
  `drop_duplicates(subset=[日期列], keep="first")`（`access.py` 的 `_compose` 路径）。
  报告期接口的响应本来就有「同一 `end_date` 多行」：`top10_holders` 是每股东一行、
  `fina_mainbz` 是每分部一行、`income`/`balancesheet` 在同一 `end_date` 下可有
  `report_type=1/6` 两行。离线读取因此只留 1 行，联网路径（直接用新鲜响应）不删。
- 复现（我自己写的最小探针，零出站）：
  ```bash
  .venv/bin/python /tmp/req011_review/dedup_probe.py
  # ① top10_holders 记录： 3 行；end_date 唯一值： 1
  #    离线读回： 1 行  ← 期望 3
  # ② income 同一期次两行（report_type 1/6）：离线读回 1 行 ← 期望 2
  #    ts_code end_date report_type  revenue
  #  600887.SH 20251231           1    100.0
  # ③ 两个不同期次的 balancesheet：离线读回 2 行 ← 期望 2   ← 只有「同期次多行」才出事
  ```
- 真实载荷佐证（用实现者自己迁好的真实仓 `/tmp/req011_real/store.db` 的只读拷贝重建）：
  ```bash
  .venv/bin/python /tmp/req011_review/real_payload_probe.py
  # top10_holders   行数=1082  日期列=end_date   唯一日期=102  最新日期=20260908 该日期行数=10
  # 我的独立重建产物里的表行数：
  #   §7. 股东与治理         数据行=1    片段=['*截至 20260908*', '', '| 序号 | 股东名称 | …', '| 1 | 香港中央结算有限公司 | 60,392.80 | 9.55 |']
  ```
  实现者自己产出的 `/tmp/req011_real/pack_600887.md` 同样是 **1 行**股东——
  `other_data.py:151` 的实现是 `df[df["end_date"] == latest].head(10)`，本来应该出 10 行。
- 判断依据：`AC-3.1` 要的是「从仓重建出 `data_pack_market.md`」，而仓是**唯一事实来源**、
  要「真正喂到下游」。买回来的 1082 行响应在产物里变成 1 行，下游（`results/prepare.py`、
  `value_analysis_engine.py`、GUI 图表）拿到的是**残缺输入**；且这是**静默**的——
  现有用例只比较 `## ` 小节标题，CI 永远绿。
  这不是设计留痕里的偏差：`DATA_LAYER_PLAN` §19.1 说的「按日期列合并去重」是**多条候选记录之间**
  的去重（同一个接口按期次各存一条时把历史拼起来），不是把**一次响应内部**的同期次多行删掉。
- 影响面不止 §7：`fina_mainbz`（§9，15 行的真实记录 → 产物写「数据缺失」）、
  同一 `end_date` 的 `income`/`balancesheet` 双 `report_type`、`dividend`
  （真实记录里最新期次 2 行 → 只剩 1 行）都会中招。

**B2（阻断，中）`AC-3.2` 的「界面」一侧没有交付：GUI 里没有任何「重建」入口**

- 现象：`scripts/webui/` 全树对 `datalayer` 的引用只有两处——`__main__.py --collect` 的转调、
  `archive/gaps.py` 的转出；三个采集面板（`plugins/collect.py`）仍是只读，没有任何
  「离线重建」按钮或路由。GUI 里唯一与采集有关的**可执行**入口是 `plugins/commands.py`
  白名单里的 `tushare_collector`（走联网取数、**会花钱**）。也就是说：界面上能触发「花钱的拉取」，
  却不能触发「不花钱的重建」。
  ```bash
  grep -rn "datalayer\|data-rebuild\|data-pull" scripts/webui/ --include=*.py
  # 只命中 __main__.py 的 --collect 转调与 archive/gaps.py 的转出；没有 rebuild
  ```
- 判断依据：`AC-5`/`AC-3.2` 的原文是「重建是**独立动作**，与「拉取」在 CLI 与**界面**上一分为二
  （不花钱 vs 花钱）」「CLI 与**界面**均可分辨」，没有「或」字。需求「## 范围」又写了
  「界面侧最多做「只读展示 + 一个触发入口」的最小接线，**或干脆留给 `REQ-012.4`**」——
  **这两处互相矛盾**。我按 `AC` 原文判**未成立**，但这需要 owner 决策（是收窄 `AC-3.2` 的
  「界面」为「留给 REQ-012.4」，还是补一个最小入口）；按 `AGENTS.md`，
  收窄验收标准属于「必须停下来问人」的事项，不由评审者自行认定。

**B3（阻断，中）迁移进来的记录与新拉取目标的键不一致：同一个仓有两个互相矛盾的完备度**

- 现象：`store.result_of(target)` 用 `param_key(target["params"])` 去撞记录；新目标带
  `report_type`/`type`/`curve_type` 等语义入参，而旧存档（`REQ-009.4`）拉这些接口时**没有**这些入参，
  于是迁移进来的记录与目标**永远对不上键**。在真实仓上：
  ```bash
  TURTLE_ARCHIVE_ROOT=/tmp/req011_review/real_probe make data-gaps ARGS='--ticker 600887.SH'
  # 完备度：22/23（有效 21 · 空 1 · 无权限 1 · 频率受限 0 · 其他错误 0）
  #   缺口 600887.SH yc_cb latest：no_permission
  .venv/bin/python /tmp/req011_review/only_gaps_debug.py
  # == 目标与重放可行性 ==
  #   income          rt=1    key=0524cfc1 records=1 replay=命中 result_of=None
  #   income          rt=6    key=08d04096 records=1 replay=未命中 result_of=None
  #   balancesheet    rt=1    … replay=命中 result_of=None
  #   cashflow        rt=1    … replay=命中 result_of=None
  #   fina_mainbz     …        records=1 replay=未命中 result_of=None
  # --only-gaps 目标： ['balancesheet','balancesheet','cashflow','fina_mainbz','income','income','yc_cb']
  # 按仓记录算的完备度（data-gaps 口径）： complete 22 / total 23
  # 按目标算的完备度（--only-gaps 口径）： complete 10 / total 17
  ```
  同一个仓、同一天，`data-gaps` 说「22/23、只有 1 个缺口」，`--only-gaps` 说「17 个目标里
  只有 10 个完备、7 个要补」。`AC-7` 要求「可查询某标的/某期次/某数据集的完备度与缺口原因」——
  两条查询路径给出不同答案，用户无法据此判断「要不要再花钱」。
- 连带：批次四类计数与实际花费不一致。把 `--only-gaps` 的目标真的跑一遍（假 pro，零出站）：
  ```bash
  .venv/bin/python /tmp/req011_review/only_gaps_debug.py
  # usage: {'new_requests': 7, 'archive_hits': 0, ...}
  # remote_calls（DataAccess 计数）: 4
  # FakePro.calls: [('yc_cb',None,None), ('income','6',None), ('balancesheet','6',None), ('fina_mainbz',None,'P')]
  ```
  7 个目标里有 3 个（`income rt=1`、`balancesheet rt=1`、`cashflow rt=1`）其实**被仓命中、
  零远程调用**，却被计成「新增请求」、`命中存档 0`——这与 `DATA_LAYER_PLAN` §19.9 写的
  「仓里已有可用记录 → 不计新增请求，计一次命中存档」相反。实跑手册第 3 步的判据是
  「新增请求为 0」，迁移之后这条判据会被计成非零。
- 另一面：真实仓里 `fina_mainbz` 明明有 600887.SH 的记录（15 行、`result=ok`），
  重建产物 §9 却写「数据缺失」，`data-gaps` 又把它算成 `ok`。原因是调用点带 `type="P"`，
  而记录既没有这个入参、响应里也没有 `type` 列 → `_filter_rows` 直接判「服务不了」
  （`无权限` 之外的第三条「仓里有但读不到」路径）。
- 判断依据：这直接顶到 `AC-2.3`（缺口查询与补齐）与需求目标 4「缺口可见可补」，
  也违反设计自己写下的「与既有 `archive/batch.py::_target_key` 的算法保持一致
  （同一套目标 → 同一个 key，迁移与续跑才能对齐）」（`DATA_LAYER_PLAN` §4.3 / §9.1）。
  同时交付的实跑记录把它解释成「旧存档里 600887.SH 没有这个数据集」，与仓内事实不符（见 `N9`）。

**B4（阻断，中）`--tier-label` 是死选项：`档位标签` 永远为空**

- 现象：`AC-3` 要求每条记录带「档位标签」。CLI 收 `--tier-label`，`PullBatch` 也收，
  但 `PullBatch.tier_label` 从不传给 `DataAccess`（`grep` 只有 `self.tier_label = tier_label` 一处赋值），
  `quota_profile` 也没有任何调用方赋值；`DataAccess._persist` 于是写空字符串。
  ```bash
  .venv/bin/python /tmp/req011_review/tier_label_probe.py   # 带 --tier-label 年包
  # balancesheet     tier_label='' quota_profile='' token_fingerprint='1a7674eb'
  # cashflow         tier_label='' quota_profile='' token_fingerprint='1a7674eb'
  # …（8 条记录全部 tier_label='' / quota_profile=''）
  ```
- 判断依据：字段在 schema 里、值恒空 ⇒ 记录并没有真正「带档位标签」；这也**回退**了
  `REQ-009.4` 已验收的存档语义（旧存档记录里 `tier_label` / `quota_profile` 是有值的，
  迁移用例 `test_legacy_import_is_idempotent` 自己断言 `imported["tier_label"] == "年包"`）。
  `DATA_LAYER_PLAN` §10.1 明确写了 `AC-4.7`「只存指纹与档位标签」不得回退。
  现有用例只在**迁移方向**断言 `tier_label`，从不在 `pull` 方向断言，所以门禁不红。

**B5（阻断，中）`hk_daily` 的窗口声明小于代码需要：重建报出的缺口用任何 pull 命令都补不上**

- 现象：`registry` 把 `hk_daily` 的窗口声明成 1 年（`window=(("years", 1),)`），
  而 `scripts/tushare_modules/financials.py:1299` 的 `_get_weekly_prices_hk` 用 **10 年**窗口
  调同一个接口（`DateOffset(years=10)`）；设计 §5.2 明确要求「声明的是**代码需要的最大窗口**」。
  后果：pull 存下 1 年窗口的记录，重建时 §11 的 10 年请求读不到 → 判缺口；
  而 `--only-gaps` 只按 `result` 判（`ok`）→ 认为完备 → 不补。
  ```bash
  .venv/bin/python /tmp/req011_review/hk_window_probe.py
  # pull 给 hk_daily 的目标参数： {'fields': …, 'start_date': '20250929', 'end_date': '20260929', 'ts_code': '00700.HK'}
  # registry 声明的 hk_daily 窗口： (('years', 1),)
  #   代码第 1225 行的窗口：DateOffset(years=10)
  #   代码第 1299 行的窗口：DateOffset(years=10)
  # 离线重建的 hk_daily 缺口： [{'dataset': 'hk_daily', 'params': {'start_date': '20160929', …}}]
  # --only-gaps 后 hk_daily 是否在目标里： False
  # store.result_of(hk_daily 目标)： ok
  # 产物末尾缺口行： ['> ⚠️ 重建缺口 8 条：hk_basic、hk_income、…、hk_daily、…']
  ```
- 判断依据：这是「缺口可查可补、完备度收敛」（`AC-2.3`/`AC-7`）的**反例**，而且是**不可收敛**的：
  `--only-gaps` 不选它；`--force` 也只会按 1 年窗口重拉一次，存下来的仍是 1 年窗口的记录；
  重建会永远报同一条缺口，而产物还在推荐 `make data-pull ARGS='--only-gaps --yes'`。
  根因与 `B3` 同源：`gaps`/`result_of` 只看 `result`，不看记录**能否服务这次请求**
  （窗口/参数兼容性），而读取路径两者都看 —— 于是「判定缺口」与「判定可读」是两套标准。

4. **N4（可追溯性，低）`pull` 写的记录 `batch_id` 恒为 `None`。** `cli.cmd_pull` 把

   `PullBatch.run` 内部新生成的，两者没有接上：

   .venv/bin/python -c "…store.records()…"   # 见 tier_label_probe 的输出片段

5. **N5（措辞，低）`data-pull --only-gaps` 在清单非空、目标全完备时打印
   「没有需要拉取的目标（清单为空或全部已 ok/empty）」。** 清单并不为空，措辞会让人以为名单丢了。
   复现：`cli_pull_probe.py` 第 5 步（`只补缺口：8 个目标中 0 个仍需补齐` 紧接
   `调用量预估：0 次请求` + `没有需要拉取的目标（清单为空或全部已 ok/empty）`）。
6. **N6（既有缺陷 + 复核陷阱，中）`PermissionError` 被当成连接错误 → 会重建**真实**客户端。**
   `datalayer/access.py::_is_connection_error` 用 `isinstance(exc, (ConnectionError, OSError))`，
   而 `PermissionError` 是 `OSError` 的子类；同时 `classify_result` 认「没有权限」是
   `no_permission`，`infrastructure.PERMANENT_ERROR_MARKERS` 却只有「没有接口 / 无权限 / …」，
   **不认「没有权限」**。于是「抱歉，您没有权限访问该接口」既不是永久错误、又被判成连接错误 →
   `DataAccess._invoke` 调 `client._new_pro_api()` 重建**真实**客户端并按上限重试。
   我就是在写探针时踩到它才误触了真实网络（见「独立复核声明」）。这是 `REQ-009.4` 搬过来的既有语义、
   `REQ-011` 没引入也没修，但现在是新门面上的默认行为，且**已有用例险险绕过**它
   （`test_data_pull.py` 用的是「抱歉，您无权限访问该接口」，含「无权限」才走永久错误分支）。
7. **N7（配置，低）GUI 读面板与数据层 CLI 的仓根解析不同源。** `datalayer.config.ENV_KEYS =

   （`scripts/webui/config.py:117`）。默认都是 `~/turtle_archive` 所以通常一致；
   但只设 `TURTLE_ARCHIVE_ROOT` 时，`--collect` 与 `make data-*` 写的是一个仓、
   只读面板读的是另一个仓。`AC-3.2`/`REQ-012.4` 的范围问题，故非阻断，但值得在 README 里说清。
8. **N8（复核方法，提示）不要用「忽略 `fields` 的假 API」对比联网与重建的逐格数值。**
   离线读取按请求 `fields` 投影（缺失列按交集处理），而假 API 整份返回 → 会出现
   `税金及附加 | 1,250.00`（联网）vs `| — |`（重建）这类差异；真机上两边请求同样的字段，
   不会出现这种差异。判据应落在真机也成立的语义上（本报告全部如此）。
9. **N9（文档准确性，低）交付的实跑记录里有一条解释与仓内事实不符。**

   请求带 `type="P"` 而记录与响应都无法确认这个入参（见 `B3`）。实跑记录里
   「没有发现需要新开子需求的缺陷」的结论因此也需要重开。

## 结论

**不通过（不能合入）。** 门禁本身是全绿的（`1787 passed, 3 skipped`、覆盖率 77.58%、
scope 43/1790 在预算内），需求的三片也有真实工程内容（仓的 schema/唯一键/迁移幂等、
批次状态机、禁网重建的骨架、口径结构化都立住了，`AC-1.1`/`AC-1.3`/`AC-1.4`/`AC-2.1`/`AC-2.2`/`AC-3.3`
可以判成立）。但：

- **B1** 是本报告最硬的一条：离线重建把「一次响应里的同期次多行」删成一行的行为，
  在**实现者自己迁好的真实资产**上就成立了（1082 行真实股东响应 → 产物 1 行股东），
  而现有用例只比较小节标题，所以 CI 永远绿。它直接破坏「原始仓是唯一事实来源、
  产物能纯离线从仓里重建」这条需求主线（`AC-3.1`），并且静默。
- **B2/B3/B4/B5** 分别打掉 `AC-3.2`（界面一侧没有交付，且与「范围」小节冲突，需要 owner 定夺）、
  `AC-2.3`（同一个仓两个互相矛盾的完备度；缺口查询与补齐判定不收敛；`hk_daily` 的缺口
  用任何 pull 命令都补不上）、`AC-3` 的「档位标签」（`--tier-label` 是死选项、
  并回退 `REQ-009.4` 的存档语义）。

修 `B1` 时请注意：不要用「把去重挪到多帧分支」这种改判定的做法糊过去——
判据应当是「一次响应内部的行**不能**按日期去重」，只有**多条候选记录之间**才需要按日期合并；
并且必须补一条**看行数**的用例（现在三片用例只看小节标题与计数，这是 B1 能溜过门禁的根因）。
修完后建议重跑一次「真实载荷的迁移 + 重建」，并在产物里核对 §7 是 10 行、§9 是多行分部。

按 `AGENTS.md`：本报告**不推进任何编号到 `verified`**；`AC-9` 的真实 token 实跑仍未由人执行；
`B2` 涉及的「收窄 `AC-3.2` 的『界面』为留给 `REQ-012.4`」属于「修改或收窄任何验收标准」，
