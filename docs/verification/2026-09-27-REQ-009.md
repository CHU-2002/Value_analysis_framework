### 本轮新发现：3 条边缘残留（都**非阻断**）

**N3a · 候选路径恰好等于 `PATH_MAX`（1024 字节）时仍 500（差一错误）**

```bash
# output_root 指向一个 785 字节深的目录（我自己在 /tmp 下建的合法目录链）
for k in 236 237 238 239; do
  curl -s -o /dev/null -w "k=$k -> %{http_code}\n" --noproxy '*' \
    "http://127.0.0.1:8809/api/v1/companies/$(python3 -c "print('a'*$k)")/artifacts"
done
# k=236（候选 1022 字节）-> 404；k=237（1023）-> 404；k=238（1024）-> 500 INTERNAL；k=239（1025）-> 403
```

原因：校验用的是 `len(os.fsencode(candidate)) > path_max`，而 macOS 的 `PATH_MAX=1024` **含结尾
NUL**，内核实际只接受 ≤1023 字节；恰好 1024 字节的候选通过了守卫，在下游
`datastore/datasets.py:155` 的 `glob` → `os.stat` 抛 `OSError: [Errno 63] File name too long`
（我取了原始 traceback 确认），成为 500。**改成 `>= path_max`（或 `path_max - 1`）即可。**
可达性：默认配置够不着——仓库默认 output 根约 70 字节、单片段又受 255 限制，候选最长约 326 字节；
只有把 `WEBUI_OUTPUT_ROOT`/`WEBUI_ARCHIVE_ROOT` 指到约 770 字节以上的深目录才可能命中。

**N3b · 指向「长/非法相对目标」的符号链接仍 500（长度守卫只看解析前路径）**

```bash
ln -s "$(python3 -c "print('a'*1000)")" /tmp/v7_out/sneaky_single     # 目标是一段 1000 字符的非法单片段
ln -s "$(python3 -c "print('/'.join(['b'*200]*5))")" /tmp/v7_out/sneaky_total   # 目标总长 1004、每段合法
curl -s -o /dev/null -w '%{http_code}\n' --noproxy '*' 'http://127.0.0.1:8808/api/v1/companies/sneaky_single/artifacts'  # 500
curl -s -o /dev/null -w '%{http_code}\n' --noproxy '*' 'http://127.0.0.1:8808/api/v1/companies/sneaky_total/artifacts'   # 500
curl -s -o /dev/null -w '%{http_code}\n' --noproxy '*' 'http://127.0.0.1:8808/api/v1/companies/sneaky_outside/artifacts'  # 403（树外目标，jail 正常）
```

原因：守卫检查的是**解析前**的 `candidate`（`<root>/sneaky_single`，很短），而 `resolve()`
（strict=False）对这类目标**不抛**；解析后的路径仍是树内（`is_within` 通过），于是下游
`glob`/`stat` 才 ENAMETOOLONG → 500。我直接验证过：`safe_join` 放行、`resolve()` 返回
1020/1024 字节的路径、`os.stat` 报 errno 63。修法：解析后再按同一组限额校验一次
`resolved`（或把 `resolve()` 的结果也纳入长度判定）。

**N3c · 合法多字节目录名被过严拒绝（本次修复引入的行为收窄，方向 fail-closed）**

```bash
# 100 个汉字 = 300 字节；APFS 实际接受（目录与其中的文件都建得出来，见复验记录）
curl -s -o /dev/null -w '%{http_code}\n' --noproxy '*' \
  "http://127.0.0.1:8808/api/v1/companies/$(python3 -c "import urllib.parse;print(urllib.parse.quote('汉'*100))")/artifacts"
# 403「路径片段超过文件系统的名字长度上限」；修复前是 200/404
```

原因：`PC_NAME_MAX=255` 在 POSIX 里按**字节**理解，而 APFS 实际按**字符/UTF-16 单元**限制，
所以 300 字节的 100 汉字名是合法的，却被守卫按字节拒了。影响：`output/<公司>` 若用超过 85 个
汉字的名字（现实中公司目录是 `<代码>_<名称>`，几乎不可能）会被面板拒之门外；方向是拒绝而非放行，
不构成越权。若 owner 在意，可改成按字符数判定或按 `os.pathconf` 的实际语义双条件判定。

**这 3 条为什么不阻断**：它们都不越界、不读出树外内容、不使服务崩溃（响应只有请求 id，
堆栈只进日志），`pages/*` 层还都能降级成 200 + warnings；`AC-6` 要求的是「不越界、拒绝
`..`/绝对路径/越界符号链接」——这些在四轮里始终成立；`AC-3.6` 枚举的失败路径也不含这些边缘输入。
按前几轮对 `V6`/`V7` 的同一口径，它们属**下一轮健壮性收敛**（可与 `V2` 的路由层收敛一起做），
不构成 `REQ-009` 的阻断项。
